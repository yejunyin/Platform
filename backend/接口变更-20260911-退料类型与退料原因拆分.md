# 接口变更说明：退料类型与退料原因拆分，审核通过回传退料类型

> 变更日期：2026-09-11
> 影响模块：M4 退料清单（接口3、接口5）、M5 质检审核（接口8、接口9）、接口7 详情返回、数据库 RETURN_TYPE 语义、M6 金蝶生产退料单生成
> 前端状态：已开发完成，等待后端同步更新
> 前置关系：**本变更推翻 2026-09-10 变更《审核通过去掉退料类型选择》中"退料类型取申请单补料原因"的方案**

---

## 一、变更背景

2026-09-10 的方案是：退料类型由后端取申请单的补料原因（REASON_ID）推导，审核端不传。

现因金蝶保存生产退料单（PRD_ReturnMtrl）时必须携带明确的"退料类型"字段，且该字段与"退料原因"是两个独立维度，方案调整为：

1. **退料类型改由发起人在退料清单页申请时选择**（独立字典，`reasonType=1`）
2. **退料原因仍由发起人选择**（独立字典，`reasonType=2`）
3. **质检员审核通过时**，前端将申请单上的退料类型（returnTypeId）随审核请求回传后端，后端写入 RETURN_TYPE 并在 M6 生成金蝶生产退料单时携带

```
退料类型(reasonType=1): 良品退料 / 不良品退料 / 报废退料 ...   ← 金蝶退料单必需字段
退料原因(reasonType=2): 生产超损耗 / 订单取消 / 换型剩余 ...   ← 业务描述字段
```

---

## 二、接口3：获取原因字典（字典语义调整 + 数据维护）

- **地址**: `GET /DBMaterialCall/getReasons?reasonType={n}`
- **封装函数**: `material-api.js - getReturnTypeList()`（reasonType=1）/ `getReasonList()`（reasonType=2）
退料类型 1 良品退料 2 来料不良退料
退料原因 TLYY01_SYS 良品退料 TLYY02_SYS 来料不良

### 2.1 参数语义变更

| reasonType | 原语义 | **新语义** |
| --- | --- | --- |
| 1 | 补料原因 | **退料类型**（金蝶退料单必需） |
| 2 | 预留 | **退料原因** |

### 2.2 返回数据（格式不变）

```json
{ "status": 0, "msg": "success", "data": [{ "id": 1, "name": "良品退料" }] }
```

### 2.3 后端工作

- 字典表需维护两套数据：`reasonType=1` 的退料类型字典、`reasonType=2` 的退料原因字典
- 若原字典表中 reasonType=1 已录入"补料原因"类数据（如"生产超损耗"），需迁移/重录为退料类型数据
- `id` 为后端字典主键（前端提交申请与审核时原样回传，后端据此落库/映射金蝶字段）

## 三、接口5：提交补退料申请（请求体新增字段）

- **地址**: `POST /DBMaterialCall/submit?username={staffCode}`
- **封装函数**: `material-api.js - submitMaterialCall(payload)`

### 3.1 请求体（新）

```json
{
  "applicantStaffId": "员工数据库ID",
  "applicantName": "申请人姓名",
  "returnTypeId": 1,
  "returnTypeName": "良品退料",
  "reasonId": 21,
  "reasonText": "生产超损耗",
  "qcStaffId": "QC1001",
  "qcStaffName": "王建国",
  "orderList": [
    {
      "orderCode": "MO20260907001",
      "materials": [
        { "materialCode": "WL0002", "materialName": "铝合金外壳", "spec": "A6061-T6", "unit": "件", "qty": 80 }
      ]
    }
  ]
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| returnTypeId | **是（新增）** | 退料类型字典ID（接口3 reasonType=1 的返回项 id） |
| returnTypeName | **是（新增）** | 退料类型文案，冗余存储供展示 |
| reasonId / reasonText | 是 | 退料原因（接口3 reasonType=2 字典），语义不变 |

### 3.2 后端处理变更

1. 服务端二次校验新增：`returnTypeId` 必填，且必须存在于 reasonType=1 字典中
2. 落库时写入 `RETURN_TYPE`（字典ID），建议同时冗余 `RETURN_TYPE_NAME`（见第六章）
3. 其余流程（生成单号、置状态10、推送质检员）不变

## 四、接口8：获取质检待审列表（返回新增字段）

- **地址**: `GET /DBMaterialCall/getAuditList?username={staffCode}`
- **封装函数**: `material-api.js - getAuditList()`

前端审核卡片新增"退料类型"展示行，审核通过时从列表项取 `returnTypeId` 回传，**因此本接口返回项必须携带退料类型**：

```json
{
  "id": "10001",
  "callNo": "TL20260911090101",
  "createTime": "2026-09-11 09:15:00",
  "applicantName": "陈明",
  "applicantDept": "装配一组",
  "returnTypeId": 1,
  "returnTypeText": "良品退料",
  "reasonText": "生产超损耗",
  "orderList": [ { "orderCode": "MO20260907001", "productName": "精密减速齿轮箱GX-200", "materials": [ ... ] } ]
}
```

| 字段 | 说明 |
| --- | --- |
| returnTypeId | **新增，必返回**。审核通过时前端回传给接口9 |
| returnTypeText | **新增，必返回**。审核卡片展示 + 审批确认框展示 |

> 兼容性：若返回项缺失 returnTypeId，前端会提示"该申请单缺少退料类型, 无法审核"并阻断通过操作（历史遗留单据处理见第七章）。

## 五、接口9：质检审核（请求体恢复 returnTypeId，核心变更）

- **地址**: `POST /DBMaterialCall/audit?username={staffCode}`
- **封装函数**: `material-api.js - auditMaterialCall(params)`（返回原始响应，前端识别 status=2 部分匹配）

### 5.1 请求体（新）

```json
{
  "id": "10001",
  "returnTypeId": 1,
  "auditStaffId": "HL202301001",
  "auditStaffName": "王建国",
  "auditResult": 1,
  "rejectReason": "",
  "forceFlag": 0
}
```

| 字段 | 说明 |
| --- | --- |
| returnTypeId | **恢复（2026-09-10 曾废弃）**。审核通过（auditResult=1）时**必传**，取自接口8列表项；驳回时前端不传 |
| auditResult | 1通过 / 2驳回 |
| rejectReason | 驳回时必填，随消息推送给申请人 |
| forceFlag | 0默认；库存不足部分匹配时前端确认后以 forceFlag=1 重发（**重发时 returnTypeId 原样保留**） |

### 5.2 后端处理变更（通过时）

1. **校验**：`auditResult=1` 时 `returnTypeId` 必填且合法；缺失时返回参数错误（status≠0，如"退料类型必填"）
2. **写入**：`RETURN_TYPE = returnTypeId`（同时更新 `RETURN_TYPE_NAME`，如有该列）
3. **M6 生成金蝶生产退料单（PRD_ReturnMtrl）时必须携带退料类型**：
   - `Save(PRD_ReturnMtrl) → Submit → Audit` 的 Model 中增加退料类型字段映射
   - "FReturnType": "1",
      "FReturnReason": {
          "FNumber": "TLYY01_SYS"
      },
   - **该字段为金蝶保存生产退料单的必需字段，缺失将导致 Save 失败（状态31）**
4. 其余流水线不变：10 → 20 批次匹配（M3）→ 30 退料单生成（M6）→ 40 → 50（WMS）→ 99

驳回逻辑不变（rejectReason 必填，不涉及退料类型）。

### 5.3 返回数据（不变）

```json
// 成功
{ "status": 0, "msg": "success", "data": { "id": "10001", "status": 99, "erpOrderNo": "TLGD...", "erpReplenishOrderNo": "BLGD...", "wmsOrderNo": "WMS..." } }

// 库存不足部分匹配（forceFlag=0时）
{ "status": 2, "msg": "库存不足", "data": { "requestQty": 1200, "matchQty": 800 } }
```

## 七、数据库变更

```sql
-- 申请主表 DB_MATERIAL_CALL
REASON_ID        INT,           -- 退料原因字典ID(reasonType=2), 发起人申请时选择(语义不变)
REASON_TEXT      VARCHAR(100),  -- 退料原因文案(不变)
RETURN_TYPE      INT,           -- 退料类型字典ID(reasonType=1): 【语义调整】由"审核时取REASON_ID写入"
                                --   改为"发起人提交时写入(接口5), 审核通过时以接口9回传值为准覆盖"
RETURN_TYPE_NAME VARCHAR(50)    -- 【建议新增】退料类型文案冗余, 供接口8/7直接返回展示
```

处理建议：
- `RETURN_TYPE` 新单据来源：接口5 提交时落库；接口9 审核通过时以前端回传的 `returnTypeId` 覆盖（校验一致后写入）
- **历史单据兼容**：存量状态=10的单据（按旧方案提交，无 RETURN_TYPE 值）：
  - 方案A（推荐）：接口8 对历史单据仍返回 `returnTypeId=null`，前端已做阻断提示，由申请人重新发起
  - 方案B：后端为存量单据提供默认退料类型（如字典第一项）并在接口8返回，允许继续审核
- 字典表：维护 reasonType=1（退料类型）/ reasonType=2（退料原因）两套数据

## 九、验证要点（联调）

1. **字典**：`getReasons?reasonType=1` 返回退料类型（如良品/不良品/报废退料）；`getReasons?reasonType=2` 返回退料原因，两套数据不混淆
2. **提交**：退料清单页不选退料类型无法提交；提交成功后数据库 RETURN_TYPE 已写入
3. **待审列表**：接口8 每项含 returnTypeId/returnTypeText，审核卡片正确展示"退料类型"
4. **审核通过**：请求体携带 returnTypeId；后端缺参时返回明确错误；通过后金蝶退料单保存成功（状态到40），在金蝶中核对退料单上的退料类型字段值正确
5. **审核驳回**：不传 returnTypeId 不影响驳回
6. **部分匹配**：status=2 后 forceFlag=1 重发（含 returnTypeId）可正常走完流水线
7. **详情**：申请记录详情正确展示退料类型 + 退料原因
