# 补退料后端更新说明：退料原因改由审核人填写 + 生产退料单计划跟踪号处理

**更新日期**: 2026-09-22
**影响服务**: 补退料独立后端服务（`http://111.2.77.144:8081`，`/DBMaterialCall/*`）
**前端版本**: 小程序补退料模块（pages/material-call、pages/material-audit）
**前端是否强制配套**: 是（前端已不再于提交接口传退料原因，改在审核接口传）

---

## 一、变更背景

1. **退料类型与退料原因分离**
   - 退料类型（字典 `reasonType=1`）：仍由**发起人**在提交申请时选择，不变。
   - 退料原因（字典 `reasonType=2`）：由原来的"发起人填写"改为**质检审核人在审核通过时填写**（必填）。
2. 补料单相关逻辑已在小程序端注释停用，本次**不涉及补料单**。
3. 金蝶 WebAPI 保存生产退料单时，可能返回交互警告：
   `单据编号 XXX 的生产退料单，序号1的分录计划跟踪号与用料清单不一致，是否继续保存？`
   WebAPI 无界面可点"是"，需后端兼容处理（见第四节）。

---

## 二、接口变更

### 2.1 提交申请 `POST /DBMaterialCall/submit`

请求体中**删除**以下两个字段（前端已不再传，后端需取消必填校验，缺失时按空处理）：

| 字段 | 原含义 | 处理 |
|------|--------|------|
| `reasonId` | 发起人选择的退料原因ID | **取消必填，忽略/置空** |
| `reasonText` | 发起人选择的退料原因名称 | **取消必填，忽略/置空** |

保留不变：`applicantStaffId`、`applicantName`、`returnTypeId`（必填）、`returnTypeName`（必填）、`qcStaffId`、`qcStaffName`、`orderList`。

提交后申请单的 `REASON_ID` / `REASON_TEXT`（或同义列）应为空，待审核通过时回写。

### 2.2 质检审核 `POST /DBMaterialCall/audit`

审核通过（`auditResult=1`）请求体**新增两个必填字段**：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `reasonId` | String | auditResult=1 时必填 | 审核人选择的退料原因ID（字典 `reasonType=2`，来源 `getReasons?reasonType=2`） |
| `reasonText` | String | auditResult=1 时必填 | 退料原因名称 |

完整请求示例：

```json
{
  "id": "申请单ID",
  "returnTypeId": "退料类型ID(发起人选择, 原逻辑不变)",
  "reasonId": "退料原因ID(审核人选择, 新增)",
  "reasonText": "退料原因名称(审核人选择, 新增)",
  "auditStaffId": "审核人工号",
  "auditStaffName": "审核人姓名",
  "auditResult": 1,
  "forceFlag": 0
}
```

后端处理要求：

1. `auditResult=1` 时校验 `reasonId`/`reasonText` 非空，缺失返回：
   ```json
   { "status": -1, "msg": "退料原因为必填项" }
   ```
2. 校验通过后，将退料原因**回写申请单记录**（原 `REASON_ID`/`REASON_TEXT` 列，写入时点从"提交"改为"审核通过"）。
3. 后续 M6 生成金蝶生产退料单时，将该原因写入金蝶生产退料单的退料原因字段（租户字典内码/名称按贵司金蝶模板映射，常见标识为 `FReturnReasonId`，请以实际 BOS 元数据为准）。
4. 驳回（`auditResult=2`）逻辑不变，仍使用 `rejectReason`，不需要 `reasonId`/`reasonText`。
5. 库存不足部分匹配（`status=2`）前端会带 `forceFlag=1` 重放，重放请求同样携带 `reasonId`/`reasonText`，后端无需特殊处理。

### 2.3 查询接口（无结构变更）

- `getAuditList`、`getMyApplications`、`getApplicationDetail` 响应字段名不变。
- 待审核单据的 `reasonText` 现在为空属正常情况，前端已兼容显示"待审核通过时填写"。

### 2.4 登录校验（无需后端改动，说明备查）

小程序打开补退料页时已在前端校验 `globalData.staffInfo.staffCode`，未登录时弹窗阻止操作。
建议后端在 `submit`/`audit` 等写接口对空 `token`/`username` 保持 401 或 `status=-1` 拦截（如已有则忽略本条）。

## 三、数据库变更（可选DDL，仅语义变更）

表结构无需新增列，仅字段写入时点变化：

| 列 | 原写入时点 | 新写入时点 |
|----|-----------|-----------|
| `RETURN_TYPE_ID` / `RETURN_TYPE_TEXT` | 提交时（发起人） | 不变 |
| `REASON_ID` / `REASON_TEXT` | 提交时（发起人） | **审核通过时（审核人）**，提交时允许为空 |

历史数据兼容：已提交且带有退料原因的老单据保留原值；审核老单据时仍以审核人新传值为准回写。
如该列当前为 `NOT NULL`，需放开空值：

```sql
-- 以实际表名/列名为准
ALTER TABLE DB_MATERIAL_CALL MODIFY REASON_ID   VARCHAR(64) NULL;
ALTER TABLE DB_MATERIAL_CALL MODIFY REASON_TEXT VARCHAR(128) NULL;
```

## 四、金蝶生产退料单"计划跟踪号与用料清单不一致"处理

生产退料单（`PRD_ReturnMtrl`）与补料单一样，分录携带计划跟踪号（`FTrackNo`）并通过 `FEntity_Link` 关联生产用料清单（`PRD_PPBOM`）。分录上的计划跟踪号与用料清单分录不一致时，金蝶保存返回交互警告（非硬错误，界面点"是"可保存），WebAPI 场景需后端主动处理。

### 方案A（推荐，根治）：保存前对齐计划跟踪号

组装生产退料单保存 JSON 时，从用料清单分录（`T_PRD_PPBOMENTRY`，按 `FPPBOMEntryId`/源单行号匹配）查询计划跟踪号，原样填入退料单分录 `FTrackNo`，保证与用料清单完全一致，警告不再出现：

```java
// 伪代码
String ppbomTrackNo = ppBomEntryMapper.selectTrackNo(entry.getPpbomEntryId());
model.put("FTrackNo", ppbomTrackNo == null ? "" : ppbomTrackNo);
```

注意：用料清单分录为空跟踪号时，退料单分录也必须传空串，不能填 null 或默认值，否则仍判不一致。

### 方案B（兜底）：识别交互警告并重放保存

金蝶 WebAPI 保存返回的 `Result.ResponseStatus` 中，需要交互确认的警告会携带交互标识（MsgId/InterationFlag）。检测到该警告时，用同一数据包在 `InterationFlags` 参数中带回该标识重新调用保存，等同于用户点击"是"：

```java
// 伪代码
SaveResponse resp = kingdeeClient.save("PRD_ReturnMtrl", json);
if (interactionNeeded(resp, "计划跟踪号与用料清单不一致")) {
    String flag = extractInteractionFlag(resp);      // 取响应中的交互标识
    json.put("InterationFlags", flag);              // 原样回传即可放行
    resp = kingdeeClient.save("PRD_ReturnMtrl", json);
}
```

说明：
- 不建议把交互标识写死，不同补丁版本标识可能不同；务必从当次响应中提取后回传。
- 参考机制：金蝶社区案例中序列号数量不一致警告即通过 `"InterationFlags": "BillSaveSNCountSpensor"` 放行；计划跟踪号警告同理，标识值以贵司环境实际返回为准。
- 方案A与方案B建议同时实施：A消除绝大多数警告，B兜底个别漏网数据。
- 重试时需保证幂等：同一申请单重复生成退料单前先校验是否已生成金蝶单号，避免重复建单。

## 五、生产退料单退料仓库/库存组织必须按领料来源还原（重要缺陷修复）

### 5.1 问题现象

102 生产组织的生产订单退料时，生成的金蝶生产退料单库存组织/仓库落到了 **100 组织**下的仓库，导致库存入错组织。

### 5.2 责任界定：后端问题

- 小程序提交/审核请求均**不包含仓库、库存组织字段**（页面无仓库选择入口），已核实前端无任何 `stockId/warehouse/FStockId/库存组织` 数据。
- 金蝶生产退料单由后端审核通过后组装 JSON 生成，退料单头库存组织 `FStockOrgId`、分录仓库 `FStockId` 均由后端赋值。
- 当前后端疑似将 `FStockOrgId`/`FStockId` 写死或取了默认组织（100）。**前端无需改动，由后端修复。**

### 5.3 修复规则：从哪里领料、退回哪里

按"生产订单分录 + 物料"查询**生产领料单**（`PRD_PickMtrl`）的实际发料记录，退料单必须使用领料单上的来源仓库：

| 退料单字段 | 取值来源（生产领料单） |
|------------|------------------------|
| 表头 `FStockOrgId`（库存组织/退料组织） | 领料单表头 `FStockOrgId`（实际发料库存组织，如 102，不得默认 100） |
| 分录 `FStockId`（仓库） | 领料单分录 `FStockId`（该物料实际发料仓库，按订单分录+物料匹配） |
| 分录 `FStockLocId`（仓位，如启用） | 领料单分录 `FStockLocId` |
| 表头 `FKeeperId`/`FOwnerId`（保管者/货主，如涉及） | 与领料单保持一致 |

参考查询逻辑（表名/字段以贵司金蝶实际库为准）：

```sql
-- 按生产订单分录+物料查最近/实际领料仓库
SELECT e.FENTRYID, e.FMATERIALID, e.FSTOCKID, h.FSTOCKORGID, e.FSTOCKLOCID
FROM T_PRD_PICKMTRL h
JOIN T_PRD_PICKMTRLENTRY e ON e.FID = h.FID
WHERE h.FDOCUMENTSTATUS = 'C'              -- 已审核
  AND e.FMOENTRYID = #{moEntryId}          -- 生产订单分录内码
  AND e.FMATERIALID = #{materialId}
  AND h.FSTOCKORGID  = #{prdOrgId}         -- 以生产组织102限定, 防止串到100
ORDER BY h.FDATE DESC;
```

Java 组装伪代码：

```java
// 退料分录逐行取领料来源仓库, 不再使用默认/写死值
PickStockInfo src = pickMtrlMapper.selectIssueStock(moEntryId, materialId, prdOrgId);
entry.put("FStockId", Map.of("FNumber", src.getStockNumber()));   // 实际发料仓库
entry.put("FStockLocId", src.getLocId() == null ? "" : Map.of("FNumber", src.getLocNumber()));
// 表头
model.put("FStockOrgId", Map.of("FNumber", src.getStockOrgNumber())); // 102 而非 100
```

### 5.4 特殊情况处理

1. **同一申请跨多个库存组织发料**（如部分料从 102 领、部分从其他组织领）：一张退料单只有一个表头 `FStockOrgId`，需**按库存组织拆成多张生产退料单**分别生成，不能强行合并到 100。
2. **同一物料多次领料、仓库不同**：以金蝶领料单分录的实际批次来源为准（如启用批次/FIFO，结合已有的批次匹配结果取该批次对应仓库）；无法唯一确定时按"最近一次领料仓库"，并记录日志便于核查。
3. **查不到领料记录**（理论上可退数量来自已领数量，不应出现）：拦截并返回明确错误，**不得回退到默认组织 100**，状态置退料单生成异常并保留错误信息。
4. 修复后需回归验证：`getOrderMaterials` 的可退数量口径与领料组织一致，避免出现 102 订单查到 100 组织库存的串数据。

## 六、上线步骤建议

1. 后端发布：放开 `submit` 的退料原因必填校验 → `audit` 增加退料原因必填校验与回写 → 金蝶退料单生成改造（计划跟踪号方案A+B、退料仓库按领料来源还原）。
2. 小程序发布新版（提交页无退料原因、审核页增加退料原因、打开页登录校验）。
3. 联调用例：
   - 发起申请（不传 reason）→ 待审核列表原因显示"待审核通过时填写"；
   - 审核通过不选原因 → 提示"请先选择退料原因"；
   - 选择原因通过 → 申请单回写原因 → 金蝶退料单生成成功且带退料原因；
   - 跟踪号不一致数据 → 退料单仍可自动生成（方案A对齐或方案B重放）；
   - **102 组织订单退料 → 退料单库存组织为 102、仓库为生产领料单实际发料仓库，不得落到 100 组织；跨组织发料时按组织拆单**；
   - 清空登录态进入补退料页 → 弹出"登录未成功"提示框。
