# 接口变更说明：质检审核通过去掉退料类型选择

> 变更日期：2026-09-10
> 影响模块：M5 质检审核（接口9）、接口6/7 返回字段、数据库 RETURN_TYPE
> 前端状态：已上线修改，等待后端同步更新

---

## 一、变更背景

原流程：审批人在审核通过时必须先选择退料类型（1良品退料 / 2不良品退料 / 3报废退料），再二次确认。

现流程：审批人点击「通过」直接弹确认框「是否确认审批通过？」，确认即提交。**退料类型不再由审核端选择，改用申请单上发起人提交时选择的补料原因（REASON_ID / REASON_TEXT）**。

---

## 二、接口9：质检审核（核心变更）

- **地址**: `POST /DBMaterialCall/audit?username={staffCode}`
- **封装函数**: `material-api.js - auditMaterialCall(params)`（返回原始响应，前端识别 status=2 部分匹配）

### 2.1 请求体（新）

```json
{
  "id": "10001",
  "auditStaffId": "HL202301001",
  "auditStaffName": "王建国",
  "auditResult": 1,
  "rejectReason": "",
  "forceFlag": 0
}
```

| 字段 | 说明 |
| --- | --- |
| auditResult | 1通过 / 2驳回 |
| rejectReason | **驳回时必填**，随消息推送给申请人 |
| forceFlag | 0默认；库存不足部分匹配时，前端经用户确认后以 forceFlag=1 重发（按最大可用量继续） |

### 2.2 删除字段

| 字段 | 处理 |
| --- | --- |
| returnTypeId | **废弃**。前端不再传递；后端收到应忽略（兼容期可兼容旧字段但不再必需） |

### 2.3 后端处理变更（通过时）

审核通过时，退料类型取申请单自身的补料原因：

1. 从申请单取 `REASON_ID`（发起人提交申请时选择，见接口5提交时上送）
2. 将其写入 `RETURN_TYPE` 字段（或直接沿用 `REASON_ID`，后续 M6 按此生成退料单）
3. 后续流水线不变：状态 10 → 20 批次匹配（M3）→ 30 退料单生成（M6）→ 40 → 50（WMS）→ 99

驳回逻辑不变（`rejectReason` 必填）。

### 2.4 返回数据（不变）

```json
// 成功
{ "status": 0, "msg": "success", "data": { "id": "10001", "status": 99, "erpOrderNo": "TLGD...", "erpReplenishOrderNo": "BLGD...", "wmsOrderNo": "WMS..." } }

// 库存不足部分匹配（forceFlag=0时）
{ "status": 2, "msg": "库存不足", "data": { "requestQty": 1200, "matchQty": 800 } }
```

## 五、数据库变更

```sql
-- 申请主表 DB_MATERIAL_CALL 无需结构变更, 仅语义调整:
REASON_ID     INT,          -- 补料(退料)原因, 发起人申请时选择(不变)
REASON_TEXT   VARCHAR(100), -- 原因文案(不变)
RETURN_TYPE   INT,          -- 退料类型: 审核通过时由后端取 REASON_ID 写入, 不再由审核端选择
```

处理建议：
- 若 `RETURN_TYPE` 与 `REASON_ID` 采用同一套字典（接口3 `getReasons?reasonType=1` 返回的原因字典），审核通过时直接 `RETURN_TYPE = REASON_ID`，或干脆废弃 `RETURN_TYPE` 列统一用 `REASON_ID`
- 若两者字典不同，需维护「补料原因 → 退料类型」的映射规则

## 六、后端改动清单（Checklist）

- [ ] 接口9 `audit`：移除 `returnTypeId` 必填校验；通过分支从申请单取 `REASON_ID` 写入 `RETURN_TYPE`
- [ ] 接口9 `audit`：兼容处理——收到旧字段 `returnTypeId` 时忽略，不报错
- [ ] 接口6 `getMyApplications`：响应删除 `returnType`，新增/保留 `reasonId`、`reasonText`
- [ ] 接口7 `getApplicationDetail`：响应删除 `returnType`，保留 `reasonText`
- [ ] 驳回分支：`rejectReason` 必填校验与消息推送保持不变
- [ ] M6 退料单生成：生成退料单时退料类型依据改为申请单 `REASON_ID`（如金蝶退料单需传退料类型字段）

## 七、验证要点（联调）

1. 审核通过：仅传 `id/auditStaffId/auditStaffName/auditResult=1/forceFlag=0`，能正常走完 10 → 20 → 30 → 40（→50）→ 99 流水线
2. 审核驳回：不传 `rejectReason` 应返回参数错误；传后正常置 11 并推送钉钉消息
3. 部分匹配：库存不足时返回 `status=2` + `{requestQty, matchQty}`，前端确认后 `forceFlag=1` 重发可成功
4. 申请记录列表/详情：前端展示「退料原因」取 `reasonText`，无 `returnType` 依赖
